第 1 课 · 接管终端

kilo-rs 课程 · Lesson 0001 · 预计 25–35 分钟 · 需要动手写代码

这一课结束时，你会有一个能接管终端、实时响应每一个按键、 并在按下 Ctrl+Q 后干净退出的 Rust 程序。 而且——这是重点——它用的是现代 Rust 的惯用法，不是把 C 版 kilo 直译过来。

本课成果

  • cargo run 后，你敲的每个键都会被程序捕获并以调试格式打印出来；
  • 按 Ctrl+Q 退出，终端恢复正常；
  • 你会亲手实现一个 Drop 守卫，理解 Rust 的资源管理哲学。

为什么需要 raw mode

默认情况下，你的终端处于「行缓冲 + 回显」模式：你输入的字符先由终端自己显示出来，直到你按回车， 一整行才交给程序。shell 正是靠这一点工作——它每次拿到的就是一整行。

编辑器不能这样。它需要三件事同时成立：

  • 每个按键立刻到达程序：你按下 j，光标要马上往下走，不能等回车。
  • 终端不要自动回显：字符显示在哪、什么颜色，由编辑器自己决定。
  • 接管 Ctrl 组合键：Ctrl+Q、Ctrl+S 不能被终端或信号处理抢先解释掉。

把终端从这种「礼貌的」模式切换到「原始」模式，这个过程就叫进入 raw mode（原始模式）。底层是通过 termios 修改一堆标志位（ICANON、ECHO、ISIG……）， 原版的 C 语言 kilo 要用几十行代码才能做到。我们把它交给 crossterm，把精力留给编辑器逻辑和 Rust 本身。

两个现代 Rust 的关键选择

在写第一行代码之前，先看两个关于「怎样才算现代做法」的决策。它们来自 Apollo《Rust Best Practices》， 也是本课程会一直沿用的风格。

① 用 RAII 守卫管理「成对出现」的操作

C 版用 atexit(disableRawMode) 和手动 exit() 来保证终端被恢复。 Rust 里没有 try/finally，取而代之、也更地道的做法是 RAII： 把「清理」写进一个类型的 Drop，只要它离开作用域，清理就一定发生—— 正常返回、? 提前返回、甚至 panic 展开，全都覆盖。

理念 这就是所有权模型在资源管理上的应用：把一个「还需要善后」的状态 编码成一个类型，让编译器替你保证善后一定被执行。后面连接池、文件句柄、事务，用的都是同一招。 （参考 Rust 官方书 第 15.3 章 Drop）

② 二进制程序的错误用 Result + ?

Apollo 手册的建议是：库用 thiserror 定义精确错误类型； 二进制用 anyhow/eyre 这类类型擦除、强调易用的方案。 本项目用仓库里已有的 color-eyre （eyre 的彩色报告版）。原则是：能返回 Result 就不要 panic，不要到处 unwrap()。

crossterm 速览

你想做的事crossterm 提供
进入 raw modeterminal::enable_raw_mode()
退出 raw modeterminal::disable_raw_mode()
等待下一个事件event::read() → Event
描述按键KeyCode / KeyModifiers

注意 event::read() 返回的 Event 是一个枚举—— 终端发出的不只是键盘事件，还有窗口大小变化（Resize）等。我们会用 let … else 只挑出键盘事件，其余直接 continue。

任务 2 写下事件循环

把 src/main.rs 清空，亲手敲一遍下面的代码（别复制——肌肉记忆也是学习的一部分）：

use std::io::{self, Write};

use color_eyre::Result;
use crossterm::{
    event::{self, Event, KeyCode, KeyModifiers},
    terminal,
};

/// Puts the terminal into raw mode; restores it when this guard is dropped,
/// whether on a normal return, an early `?` return, or a panic unwind.
///
/// Intentionally a unit struct: raw mode is process-wide terminal state with no
/// handle to hold. The only point of this type is to make `Drop` fire at the
/// right moment.
struct RawModeGuard;

impl RawModeGuard {
    fn enter() -> io::Result<Self> {
        terminal::enable_raw_mode()?;
        Ok(Self)
    }
}

impl Drop for RawModeGuard {
    fn drop(&mut self) {
        // `Drop` must not panic, or the panic during unwinding would double-panic
        // and abort. So we explicitly ignore the error.
        let _ = terminal::disable_raw_mode();
    }
}

fn main() -> Result<()> {
    color_eyre::install()?;
    let _guard = RawModeGuard::enter()?;

    loop {
        let Event::Key(key) = event::read()? else {
            continue;
        };

        if !key.is_press() {
            continue;
        }

        match key.code {
            KeyCode::Char('q') if key.modifiers.contains(KeyModifiers::CONTROL) => break,
            _ => {
                print!("{key:?}\r\n");
                io::stdout().flush()?;
            }
        }
    }

    Ok(())
}

逐段拆解，重点在为什么这么写：

  • fn main() -> Result<()>：这里的 Result 来自 color_eyre。 main 返回它，就可以在里面用 ? 传播任何实现了 Error 的错误。 Apollo 手册明确推荐：二进制用 anyhow/eyre 这类方案。
  • struct RawModeGuard; + impl Drop：本课的灵魂。它没有字段， 「进入 raw mode」和「退出 raw mode」这两件必须成对的事被绑在一个作用域上。
  • let _guard = RawModeGuard::enter()?;：变量名以 _ 开头而不是就叫 _， 这是个易错点——_ 会立刻丢弃值，_guard 会活到main结束， 从而保证 Drop 触发。
  • let Event::Key(key) = event::read()? else { continue };：let … else 是 Rust 1.65 引入的现代写法，专门用于「模式不匹配就做一件简单的事（这里是跳过）」。 比 if let … { } else { } 少一层缩进，意图更清晰。 （参考 Apollo 手册 §1.3）
  • key.is_press()：Windows 会同时发出按下和松开事件，macOS/Linux 默认只有按下。 加这一行让判断跨平台正确。
  • match key.code 加 guard if key.modifiers.contains(...)： 只有字符 'q' 且带 Control 修饰才退出。KeyModifiers 是 bitflags，用 .contains() 判断。
  • print!("{key:?}\r\n")：{key:?} 是内联格式参数（1.58+）， 比 print!("{:?}", key) 更简洁。
  • \r\n 而不是 \n：raw mode 关掉了输出的「后处理」（OPOST）， 单独一个 \n 只换行不回车，会一路向右缩进成楼梯。
  • io::stdout().flush()?：确保内容立刻写出去，不被缓冲吞掉。

任务 3 运行并观察

cargo run

然后依次做这几件事：

  1. 随便敲几个字符，比如 a、方向键 ↑、Ctrl+S。 你会看到形如 KeyEvent { code: Char('a'), modifiers: NONE, ... } 的输出。
  2. 注意：终端不会回显你敲的字符本身，只显示程序打印出来的结构体——这正是 raw mode 在起作用。
  3. 按 Ctrl+Q 退出，回到 shell，一切正常。

如果顺序不对（没退出、或退出后终端怪怪的），把现象记下来，直接问我。

如果程序崩了，终端会怎样

重要 守卫救的是「终端状态」，救不了「panic 输出的排版」

有了 RawModeGuard，即使程序 panic，Drop 也会在栈展开时执行，终端一定被恢复。 但有个细节：panic 报告是在 Drop 之前打印的，那时还在 raw mode，\n 不回车， 所以报告看起来会排版错乱。这正是下一课要加 panic hook 的原因——干净的报错也是现代应用的一部分。

万一真遇到终端没恢复：盲打 reset 或 stty sane 再回车（看不见字也会执行）， 或直接关掉这个终端标签页。

挑战（强烈建议） 亲手验证 Drop 在 panic 时也会跑

在 let _guard = RawModeGuard::enter()?; 后面临时加一行 panic!("boom");， cargo run。你会看到 panic 报告（排版可能是乱的），然后——终端是好的， shell 可以正常用。这就是 RAII 的威力：你并没有写任何「出错时怎么办」的代码。

做完把 panic! 删掉。进阶对比（可选）：把 let _guard = RawModeGuard::enter()?; 换成 terminal::enable_raw_mode()?;，再加 panic!("boom");，你会发现终端这次真的坏了。 差别就在那个守卫。

小测：先回忆，再对答案

合上上面的内容，试着回答，再展开 details 对答案。回忆越费力，记得越牢。

1. raw mode 主要关掉了终端的哪些行为？

  • 行缓冲与自动回显
  • 方向键与功能键识别
  • 窗口大小变化事件
  • 标准输出的刷新时机
看答案

第一个。raw mode 关掉的是输入的行缓冲（ICANON）、自动回显（ECHO） 和信号处理（ISIG）。方向键仍然可用，而且因为不再被终端「吃掉」，crossterm 反而能更好地 把它们解析成 KeyCode。

2. 为什么绑定的名字叫 _guard，而不是直接写 _？

  • _ 会立刻丢弃值，_guard 会活到作用域结束
  • _ 是保留字，不能承接实现了 Drop 的值
  • 两者完全等价，_guard 只是更好读一点
  • _guard 会让编译器跳过硬件的 Drop 检查
看答案

第一个。这是 Rust 里一个经典陷阱：let _ = ... 是「立刻丢弃这个值」， let _guard = ... 才是「绑定它、活到作用域结束」。写错的话守卫会在那一行就析构， 终端立刻被恢复，raw mode 等于没开。

3. 如果 event::read()? 返回 Err 让 main 提前返回，谁负责恢复终端？

  • RawModeGuard 离开作用域时自动恢复
  • 程序会 abort，终端无法被恢复
  • 必须在每个 return 前手动调用
  • 终端驱动会检测进程退出并自动恢复
看答案

第一个。这就是把清理放进 Drop 的意义：无论从哪条路径离开作用域，清理都执行。 终端驱动不会替进程恢复 termios 状态。
