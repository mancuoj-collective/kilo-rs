kilo-rs 课程 · Reference 0003 · 现代 Rust CLI 的模块划分

这一页回答两个问题：什么时候该分文件，以及 kilo-rs 最终长什么样。 它不是「现在就把代码拆成这样」的指令，而是一张地图——拆分的时机到了，照着它走。

一、什么时候分文件：按「接缝」，不按行数

「文件太长了」不是拆分的理由。拆分的依据是能不能画出一条干净的接缝（seam）—— 接口画在哪里，才能让调用方少学一点、维护者少找一点。

词汇 深模块＝小接口 + 大量实现。少数几个方法背后藏着一堆逻辑， 调用方（和测试）只需要学那点接口。反过来，接口和实现一样复杂，就是浅模块，是负担。
拆分的价值来自深：接口小 → 调用方省力；实现集中 → 维护和测试都在一处。

出现这些信号，就该拆了

  • 一组函数共享隐藏的状态或不变式。例如终端守卫：raw mode、备用屏幕、光标必须成对开关—— 这是一个概念，不是三个函数。
  • 它在领域里有名字：Document（缓冲区）、Row（一行）、Cursor（光标）、Syntax（高亮规则）。 「能被命名的东西」通常就是一层接缝。
  • 你希望能通过一个小接口测试它。
  • 删除测试：假设删掉这个模块，如果复杂度消失了，它是多余的；如果复杂度在 N 个调用方重新冒出来， 它就是在挣饭吃。

这些是反模式

  • 按行数拆：拆出来一堆浅模块，接口和实现一样大。
  • 按技术层拆（models / services / utils）：Rust 里尤其糟——utils.rs 是垃圾桶。
  • 过早抽象：第一次出现就抽接口。等第三次出现，形态才会清晰 （Martin Fowler 的「Rule of Three」）。重复两行代码，比错误的抽象便宜得多。

二、现代 Rust 二进制的三条结构原则

① main.rs 要薄

真正的 main 只做三件事：初始化（color-eyre）、解析参数、调用一个入口函数， 然后把错误映射成退出码。业务逻辑一行都不该在这里。

② lib.rs + main.rs：把逻辑放进库

把逻辑放在 src/lib.rs 及其模块里，main.rs 只是一个几行的二进制外壳。 这样 tests/ 里的集成测试可以直接 use kilo::… 调用你的逻辑—— 这是「二进制也能被测试」的关键一招，也是初学者最常忽略的结构优点。

诚实地说 这不是唯一写法，也不是硬性要求。 唯一的技术理由是：tests/（集成测试）和 benches/ 只能链接库，链不到二进制。 单元测试（#[cfg(test)] mod tests）在纯二进制的 crate 里照样能跑， 所以很多小 CLI 只写 main.rs + 模块，同样是现代做法——别 cargo-cult。

决策规则：需要黑盒测试 / 基准 / 复用为库 → 用 lib.rs； 只需要单元测试 → main.rs + mod 就够。

本项目选 lib.rs，是因为「编辑器核心」值得在无终端的环境下跑集成测试 （全屏 TUI 没法用 assert_cmd 那样黑盒跑）。代价是 main 只能看到 pub 项， 所以我们只暴露一个 pub fn run() 把接口收窄，而不是把内部函数都标 pub。

③ 按领域概念分模块，可见性收紧

模块对应「概念」，不对应「层」。跨模块可见性默认用 pub(crate)， 只有库真正对外暴露的 API 才用 pub——接口的边界由可见性强制划定。

文件命名：Rust 2018 之后用 foo.rs + foo/ 目录，不要再写 mod.rs。

三、kilo-rs 目标结构

kilo-rs/
├── Cargo.toml
└── src/
    ├── main.rs        # thin: color-eyre + call into the library
    ├── lib.rs         # module declarations; the real entry point
    ├── tui.rs         # terminal lifecycle: raw mode / alt screen / cursor / panic hook
    ├── editor.rs      # editor state: cursor, viewport scrolling, buffer contents
    ├── document.rs    # buffer: lines, insert/delete, load/save (domain model)
    ├── row.rs         # one line + render expansion (tabs, highlight spans)
    ├── ui.rs          # pure rendering: &Editor -> terminal (stateless)
    └── syntax.rs      # syntax highlighting rules

对照原版 C kilo：它的 editorConfig E; 是全局变量，所有函数都直接读写它。 我们的做法是把状态装进 Editor，通过 &mut Editor 传递—— 所有权和可变性由类型系统管，而不是靠约定。

四、每个模块的接口草图

看接口有多小：这正是「深」的含义。

模块接口（大致）藏起来的实现
tui Terminal::enter() -> io::Result<Terminal>、Drop、install_panic_hook()、size() raw mode、备用屏幕、光标、panic 恢复
document Document::open(path)、line(i) -> Option<&str>、insert_char、insert_newline、delete_char、save、is_dirty 行的存储、UTF-8 处理、脏标记、文件 I/O
row Row::from(&str)、render() -> &str、cx_to_rx、rx_to_cx tab 展开、高亮片段、坐标换算
editor Editor::new(lines)、move_cursor(Move)、scroll(rows, cols)、cursor() / viewport() 光标位置、视口滚动、缓冲区内容
ui draw(editor: &Editor, out, area) 逐行输出、status bar、message bar
syntax Syntax::for_path(path)、highlight(row) -> Vec<Span> 关键字表、注释/字符串状态机、颜色

注意 editor 与 ui 的分工 editor 是状态 + 行为， ui 是纯函数式的渲染。让渲染只读 &Editor、不改变状态， 你就能为它写「给定状态 → 期望输出」的测试，以后也能替换渲染后端。这是「返回结果，而不是产生副作用」。

五、拆分路线图（和课程对应）

  1. 第 4 课：tui.rs + lib.rs（已完成）。终端守卫独立，逻辑进库，从此能写测试。
  2. 第 5 课：editor.rs（已完成）。光标与视口状态收进 Editor，并开始写单元测试。
  3. 第 6 课：row.rs（已完成）。一行文本 + 「字符 ↔ 显示列」换算，为 tab 与宽字符打地基。
  4. 编辑功能到来时：document.rs。 插入、删除会让「缓冲区」长出一组共享不变式的方法——那时它就是深模块。
  5. 状态栏 / 消息栏：ui.rs。渲染逻辑攒够了，抽成只读 &Editor 的函数。
  6. 语法高亮：syntax.rs。规则表 + 状态机，独立成模块。

原则 每一刀都是「行为不变的搬家」：先让现有功能继续跑通（可编译、可运行）， 再搬家，搬完再跑一次。绝不「一边重构一边加功能」。这就是为什么拆分要等接缝清晰—— 接缝不清楚时搬家，就是在制造错误的抽象。
