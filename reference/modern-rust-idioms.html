这不是语法教程，而是本课程刻意采用的现代写法速查。依据主要是 Apollo《Rust Best Practices》 与 Rust API Guidelines。 遇到「hecto 是那样写的，但我们这样写」时，来这里查理由。

1. import 的顺序

约定：std → 空行 → 外部 crate → 空行 → 本 crate（crate:: / super::）。 rustfmt 的 group_imports = "StdExternalCrate" 能自动做，但目前要 nightly 才完全生效， 所以先手工遵守。

use std::io::{self, Write};

use color_eyre::Result;
use crossterm::terminal;

use crate::document::Document;

2. let … else：模式不匹配就提前离开

当「不匹配」是正常、可预期的情况（continue / break / return）， 用 let … else（Rust 1.65+），不要用 if let … { } else { } 套娃。

场景选择
失败分支要做额外计算，且需要那个值if let … else { … }
失败分支只是 continue/break/returnlet … else { … }
需要分别处理 Ok 和 Err 的不同形态match
 
// ❌ 别扭
if let Some(row) = self.row(idx) {
    process(row);
} else {
    return;
}

// ✅ 现代
let Some(row) = self.row(idx) else {
    return;
};
process(row);

视角 一行里常常有两层失败，别混为一谈：

  • expr? 处理 Result/Option 层——出错就从当前函数返回（不是跳出循环）。
  • let PATTERN = … else { … } 处理枚举变体层——模式不匹配时就跑 else 块。

例：let Event::Key(key) = event::read()? else { continue }; = 先用 ? 处理 I/O 错误，再用 else 跳过非键盘事件。else 块必须发散 （continue/break/return/panic!）。

3. RAII 与 Drop：资源清理的默认手段

Rust 没有 try/finally。凡是「必须成对出现」的操作（进入/退出 raw mode、 加锁/解锁、开事务/提交或回滚），都用一个类型把清理放进 Drop。 作用域一结束——正常、? 提前返回、panic 展开——清理都会执行。

struct RawModeGuard;

impl RawModeGuard {
    fn enter() -> io::Result<Self> {
        terminal::enable_raw_mode()?;
        Ok(Self)
    }
}

impl Drop for RawModeGuard {
    fn drop(&mut self) {
        // Drop 不能 panic，否则展开中的 panic 会二次 panic 导致 abort
        let _ = terminal::disable_raw_mode();
    }
}

陷阱 let _guard = … 会活到作用域结束； let _ = … 会立刻丢弃。守卫变量必须带名字。

顺序 守卫必须在「可能失败的操作」之前构造； 成功时要把守卫移出去（Ok(guard)，不是 Ok(Self)）， 否则它会在函数里提前析构，等于清理没被推迟、资源刚开就被关。

4. 错误处理

  • 能返回 Result 就不要 panic；不要在生产代码里 unwrap()/expect()。
  • 用 ? 传播错误，而不是 match 层层手写。
  • 二进制用 eyre（本项目是 color-eyre）或 anyhow； 库用 thiserror 定义精确错误类型。
  • 需要给错误加语境时用 .context("…")?（color-eyre/anyhow 都支持）。
fn main() -> color_eyre::Result<()> {
    color_eyre::install()?;
    // ...
    Ok(())
}

为什么内部函数用精确错误类型？

io::Result<T> 是 Result<T, io::Error> 的别名； color_eyre::Result<T> 的 E 是 eyre::Report（能装任意错误）。 ? 会自动调用 From 把具体错误转成 Report，所以两种类型可以混用。

位置返回类型理由
小的内部函数（如 enter()）io::Result<Self> 等具体类型 失败面精确、信息不丢、不耦合上层错误库
main / 应用边界color_eyre::Result<()> 汇总多个来源、统一漂亮地展示给人看

口诀：错误类型尽量窄地往下沉，只在边界擦除。

旧写法现代写法
print!("{:?}", key)print!("{key:?}")（内联格式参数，1.58+）
#[allow(clippy::x)]#[expect(clippy::x)]（问题消失时会反过来提醒你）
lazy_static!std::sync::OnceLock
once_cell::Lazystd::sync::LazyLock（1.80+）
unwrap() 用于「不可能失败」优先 ?；确实不可能失败时 expect("原因")
.clone() 绕过借用检查先想清楚所有权，尽量用 &T / &str / &[T]

字符串转换：to_owned / from / to_string

对 &str → String，三者结果和性能完全一样，区别在来源与语义：

写法来源该用在哪
str::to_owned(s)ToOwned（Clone 的 ?Sized 推广） 迭代器链、泛型、Cow：类型无关，写法统一
String::from(s) / s.into()From<&str> 显式转换，或需要 Into 的场合
s.to_string()ToString / Display 把实现了 Display 的值渲染成文本

陷阱 对 &&str 调 .to_owned() 得到的是 &str，不是 String （因为 &str: Clone ⇒ ToOwned for &str 的 Owned = &str）。 用函数路径 str::to_owned 可避开歧义——它明确是 fn(&str) -> String。

6. 注释与文档

  • // 解释「为什么」，不解释「做了什么」。命名好的代码自己会说做了什么。
  • 公开 API 用 /// 文档注释，写清用途、错误（# Errors）、panic（# Panics）。
  • 约定开头的具名注释：// SAFETY:、// PERF:、// CONTEXT:。
  • // TODO 要关联 issue，不要悬空。
